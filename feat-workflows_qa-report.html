End-to-end test of the chatbase CLI against the pairing-login preview deployment, across four permission phases: all permissions, read-only, a custom asymmetric scope set, and a restricted read+dead-scope set.

A · Backend — check these request IDs in Axiom

A1

Training an agent with zero sources returns a 500 bug

chatbase agents train <id> on an agent with no sources → INTERNAL_SERVER_ERROR. Should be a 4xx domain error ("agent has no sources to train"), like the clean AGENT_NOT_TRAINED that auto-retrain already returns.

Localhost repro (2026-08-17): reproduced against a local dev backend (request id 97fc4e4a-fce5-47f1-93d8-1c8f2e2cbbc7 — the chatbase-server response body is in the dev terminal). Mechanism: train-agent.handler.ts proxies to chatbase-server's /trainings/… and maps every non-"Chatbot is training" failure to 500 (triggerAgentTraining result). Fix: pre-check for zero trainable sources and return a 4xx, or classify chatbase-server's zero-sources body the way the in-flight-training 400 already is.

request id fra1::7pwzg-1786894797640-bb4ef9e07990

Multipart POST /agents/:id/sources with CHATBASE_FILES_URL pointed at the Vercel preview → INTERNAL_SERVER_ERROR. Round 2 update: uploads work when pointed at the dedicated staging files service (api-staging-5ef3.up.railway.app) — create, replace (PUT), and sync creates all pass, and it accepts preview-issued keys. So the remaining question is only why the Vercel preview's route 500s (or whether it should exist at all).

A5

QnA sources require name; text sources don't contract

Creating a qna source without a name → VALIDATION_INVALID_BODY ("name: expected string, received undefined") while text sources default the name. Make the contract consistent, or see C4 for the client-side guard.

A6

Permission errors never name the missing scope polish

AUTH_INSUFFICIENT_PERMISSIONS says only "You don't have permission to perform this action." Including the required scope (e.g. "requires agents:write") would save every scoped-key user a support round-trip. Related docs gap: the public API reference (checked get-sources-summary) documents auth as just "Bearer token" and never lists per-endpoint required scopes — e.g. summary actually requires sources:read. The response schema itself matches live behavior exactly.

A7

chatlogs:delete is grantable but unusable polish

The activate page offers a chatlogs:delete scope, but the public OpenAPI spec has no conversation-delete endpoint and the CLI has no command for it. Dead scope from the user's perspective — remove it from the picker or ship the endpoint.

A8

Upload API rejects file types and sizes that real docs folders contain contract

Allowed types are only .pdf, .docx, .doc, .txt, .json — no .md, .html, or .csv, which is what documentation directories are mostly made of (see B6 for the CLI side). There is also a 50-byte minimum that rejects legitimate small files (INVALID_BODY: "File size must be between 50 bytes and 20 MB"). Consider allowing markdown at minimum, and reconsider the size floor.

B · CLI code

B1

File uploads ignore CHATBASE_API_URL and leak keys across environments fixed in dc3ebc4 (warn)

Uploads go to hardcoded files.chatbase.co (src/client/files.ts:8), overridable only by the separate, undocumented-in-help CHATBASE_FILES_URL. Testing against a preview therefore sends the preview-issued key to production, which 401s — and quietly transmits a credential to an environment it wasn't issued for.

when CHATBASE_API_URL is set and CHATBASE_FILES_URL isn't, derive the files base from the API base (or at minimum warn, as auth status already does for the API override).

B2

ID-as-flag commands produce a misleading "not a chatbase command" fixed in dc3ebc4

agents get <id> and sources get <id> take positional IDs, but conversations get and messages feedback require --conversation/--message flags. Typing conversations get <id> — the obvious form — exits 127 with "not a chatbase command" from the not-found plugin.

accept the conversation ID positionally on both commands, or at least make the strict-args error suggest the flag form.

B3

Top-level help shows wrong descriptions for agents and sources fixed in dc3ebc4

chatbase --help describes the agents topic as "Enable or disable automatic retraining…" and sources as "Create a source…" — oclif falls back to the alphabetically-first subcommand when a topic isn't declared.

add agents and sources entries to oclif.topics in package.json.

B4

QnA create doesn't require --name client-side fixed in dc3ebc4

The CLI sends the request and lets the server 400 (see A5). Validate in src/commands/sources/create.ts so the user gets an instant exit-2 usage error instead.

B5

--verbose is silent on the file-upload path fixed in dc3ebc4

The upload client (src/client/files.ts) emits no diagnostics with --verbose — exactly where they were needed to debug B1. Log the resolved host and status like the main client does.

B6

sources sync defaults include file types the API always rejects fixed in dc3ebc4

DEFAULT_INCLUDE in src/sync/diff.ts:24 lists **/*.md, **/*.html, **/*.csv — three extensions the upload API refuses (A8). A default sources sync over a typical docs folder is therefore guaranteed to end in partial failure with exit 1, every run. Sync also doesn't pre-check the 50-byte minimum.

align DEFAULT_INCLUDE with the API's allowed list (or pre-filter with a per-file "skipped: unsupported type" warning), and skip under-minimum files in the plan. If the API grows .md support instead, update the defaults together.

B7

Tickets subcommands disagree on how to name the ticket fixed in b362288

tickets get 769 and tickets update 769 take the ticket number positionally, but tickets messages and tickets reply require a --ticket flag. The natural tickets messages 769 exits 127 with the same misleading "not a chatbase command" as B2.

accept a positional TICKETNUMBER on messages and reply too (keep --ticket as the alternative, same pattern as the B2 fix).

B8

tickets create can't succeed without hand-written JSON fixed in b362288

The API requires customer (an object with email), but the CLI offers no flag for it — --subject + -f description=… always 400s with VALIDATION_INVALID_BODY (request id fra1::6ktjg-1786975280128-f9cbe3c0e88f). Only --data '{"customer":{…}}' works. The --data help also under-documents the body: create's omits statusCategory/assigneeId/assigneeEmail, update's omits assigneeEmail.

add --customer-email/--customer-name flags (mirroring reply's --author-email), and fix both --data field lists.

B9

config set agent looks broken when an env var shadows it fixed in b362288

Setting the agent (typed or via the arrow-key picker) writes user config — the lowest precedence tier (-a flag > CHATBASE_AGENT_ID > chatbase.json > user config). With CHATBASE_AGENT_ID exported, the set succeeds silently but every command keeps using the env value, which reads as "set doesn't overwrite".

after a successful set, warn when CHATBASE_AGENT_ID or a project chatbase.json outranks the stored value, naming the shadow.

C · UX polish

C1

get commands print a list row, not a detail view

agents get and sources get output the same single tab-row as list, while the API returns a rich object (instructions, status, autoRetrain, lastTrainedAt, styles…). Human mode should show a key-value detail view.

C2

Raw epoch seconds in human output

conversations list and messages list print timestamps like 1786895001. Format as ISO or relative time in human mode; keep epoch for --plain/--json.

C3

Empty lists print nothing at all

An empty conversations list exits 0 with zero bytes. Correct for scripts, but human mode should say "No conversations found" on stderr.

C4

No way to unset a config key cleanly

config set agent "" works but prints ✓ agent set to (trailing blank) and stores "agent": "" in the config file. Add config unset or a "cleared" message.

C5

sources summary prints raw JSON blobs as cells

Rows like links {"count":1,"size":0} — flatten to columns in human mode.

C6

chat retry silently discards later messages

Retrying an earlier message truncates the conversation after it and re-issues message IDs (a follow-up exchange vanished during testing; stored message IDs went stale for messages feedback). Correct regenerate semantics — but the help text should warn about it.

C7

auth status exits 0 when logged out

Scripts can't use it as an auth probe. gh auth status exits 1 in the same situation — consider matching.

C8

Base flags leak into help where they don't apply

health --help advertises -f, --field ("Set a body field") on a command with no body.

C9

sources sync prints every failure twice

Each failed file appears once inline as it happens and again in the trailing "Failures (N)" block — double the noise on a mostly-failing run. Keep the summary, drop the inline duplicates (or vice versa).

C10

chat "message" exits 127 with "not a chatbase command" fixed in 3b12b18

Because chat is both a command and a topic (chat retry), a positional message is resolved as a subcommand name and falls into the not-found plugin — same misleading-error family as B2/B7. The message must go via -m (or stdin), but nothing tells the user that.

C11

agents train ignores the configured default agent fixed in 3b12b18

It requires a positional AGENTID (consistent with agents get/delete) but, unlike every -a-style command, offers no fallback to CHATBASE_AGENT_ID / config — chatbase agents train alone is an exit-2 error.

Code-review cross-check — live verification of the feat/workflows review

The 12-agent code review of this branch (feat-workflows_review.md / _solutions.md) reported 24 real issues. The highest-impact ones were re-tested against the running preview; five reproduced exactly as predicted:

R1

REPL /retry is completely broken confirmed live

Review #1/#10: the REPL hardcodes messageId: 'last', a sentinel the retry endpoint doesn't implement. Reproduced: send a message in the REPL, type /retry → ✗ Message not found in conversation, every time. The solutions doc's fix (capture the assistant messageId from the stream's finish metadata) is the right shape.

R2

Sync never converges for non-plain-text files fixed in 6f3d761

Review #7: change detection compared local raw bytes to the remote extracted-text size. Reproduced: synced a 620-byte PDF, then an immediate --dry-run re-plan showed ~ tiny.pdf forever. Fixed: the backend now exposes the raw upload size (FileMetadata.originalSize) and the sync diff prefers it, falling back to the extracted size only for sources that predate the field (which self-heals — the first re-upload stamps the value). Live-verified: the same PDF now converges (~0 updated, 2 unchanged).

R3

--include filters turn sync into a delete trap confirmed live

Review #26: filters narrow the scan but not the delete set. Reproduced: sources sync --include '**/*.pdf' --dry-run planned − three.txt while three.txt sat right there on disk. With --force (the documented CI mode) that delete executes with no confirmation.

R4

ANSI escape injection via --resume replay confirmed live

Review #17: stored user messages are replayed to the terminal unsanitized. Reproduced: seeded a conversation with a message containing raw ESC[31m bytes; the REPL's resume banner delivered them verbatim to the terminal — the injected sequence even terminated the CLI's own dim formatting mid-line. OSC 52 clipboard writes would ride the same path.

R5

--resume silently ignored outside the REPL confirmed live

Review #15: chat -m "…" --conversation <id> --resume runs successfully with no history replay and no warning that the flag did nothing.

R6

Remaining review findings are code-verified, not live-tested

The SSE parser swallowing mid-stream error events (#3/#11/#25), the unabortable 429 backoff (#14), concurrent-sync duplicates (#9), and the rest need fault injection to reproduce; the review's server-source traces are convincing on their own. Note #25's evidence also upgrades this report's B5: --verbose is declared but never read anywhere in src/ — the flag is entirely dead, not just on the upload path.
